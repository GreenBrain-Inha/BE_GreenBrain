# Architecture Decision Records

## 철학

MVP 속도 최우선. 작동하는 최소 구현을 선택한다. 외부 의존성은 꼭 필요한 것만 추가하고, 나중에 교체 가능한 구조를 유지한다.

---

### ADR-001: FastAPI 선택 (백엔드 프레임워크)
**결정**: Python 백엔드 프레임워크로 FastAPI를 사용한다.
**이유**: ecologits와 OpenAI SDK가 모두 Python 기반이라 언어를 통일할 수 있다. Pydantic 스키마로 요청/응답 검증이 자동화되고, 자동 생성 OpenAPI 문서가 프론트엔드와의 협업에 유리하다.
**트레이드오프**: Django보다 배터리 포함 기능이 적어 인증, 마이그레이션 등을 별도로 구성해야 한다.

---

### ADR-002: Supabase / PostgreSQL 선택 (데이터베이스)
**결정**: 데이터베이스로 Supabase(PostgreSQL)를 사용하고, 비즈니스 로직은 FastAPI에 둔다.
**이유**: PostgreSQL의 안정성과 Supabase의 빠른 프로비저닝을 활용해 MVP 셋업 시간을 줄인다. Supabase Row Level Security 등 고급 기능은 사용하지 않고 데이터 영속성 레이어로만 활용한다.
**트레이드오프**: Supabase 특화 기능(Realtime, RLS)을 포기한다. 비즈니스 로직을 FastAPI에 집중시키므로 Supabase를 다른 DB로 교체해도 영향이 최소화된다.

---

### ADR-003: 좋아요 보상 일일 상한 60 토큰
**결정**: 좋아요로 회복할 수 있는 토큰은 하루 최대 60개로 제한한다.
**이유**: 상한 없이 좋아요 보상을 허용하면 토큰 소진의 의미가 사라진다. 사진 업로드 보상(챌린지 3개 × 20 = 최대 60)과 좋아요 보상(최대 60)을 합해 하루 최대 120 토큰까지 회복 가능하게 설계해 행동 유도와 제한 사이의 균형을 맞춘다. 단, `daily_token_state.tokens_remaining`은 일일 기본 토큰 한도인 150을 초과하지 못하도록 클램핑한다.
**트레이드오프**: 활발한 사용자가 좋아요를 많이 받아도 일정 이상 채팅을 복구할 수 없다.

---

### ADR-004: 챌린지 사진 검증을 커뮤니티 좋아요로 대체
**결정**: 챌린지 인증 사진의 진위 검증을 AI(GPT Vision) 대신 커뮤니티 좋아요로 대체한다.
**이유**: GPT Vision 호출은 비용과 지연이 발생하고, MVP에서 검증 기준을 정의하기 어렵다. 커뮤니티 좋아요는 구현이 단순하고 동시에 사용자 참여를 유도하는 부수 효과가 있다.
**트레이드오프**: 허위 인증 사진을 막지 못한다. MVP에서는 이를 허용하고, 어뷰징이 실제 문제가 될 때 검증 로직을 추가한다.

---

### ADR-005: JWT를 HttpOnly 쿠키에 저장
**결정**: 인증 토큰을 localStorage 대신 HttpOnly + Secure 쿠키에 저장하고, 만료는 30분으로 설정한다.
**이유**: HttpOnly 쿠키는 JavaScript로 접근할 수 없어 XSS 공격으로부터 토큰을 보호한다. SameSite=Strict로 CSRF도 방어한다.
**트레이드오프**: 모바일 앱이나 서드파티 클라이언트에서 쿠키 기반 인증을 다루기 번거롭다. MVP는 웹 전용이므로 문제없다.

---

### ADR-006: 파일 저장 추상화 인터페이스 (FileStorage Protocol)
**결정**: 파일 저장을 `FileStorage` Protocol 인터페이스로 추상화하고, MVP는 로컬 FS, 프로덕션은 S3 호환 스토리지로 전환한다.
**이유**: MVP에서 S3를 바로 쓰면 설정 복잡도가 높아진다. 인터페이스를 먼저 정의해두면 로컬 FS로 개발하다가 코드 변경 없이 S3로 교체할 수 있다.
**트레이드오프**: 인터페이스 계층이 하나 추가된다. 단순한 MVP에는 오버엔지니어링처럼 보일 수 있지만, 프로덕션 전환 비용이 훨씬 크다.

---

### ADR-007: 일일 토큰 초기화를 Lazy Initialization으로 처리
**결정**: KST 자정 기준 일일 토큰 초기화를 별도 크론 잡 없이, 요청 시점에 오늘 날짜 행이 없으면 FastAPI가 기본값(150 토큰)으로 생성하는 방식으로 구현한다.
**이유**: MVP에서 크론 잡 인프라를 별도로 운영하는 것은 복잡도 대비 효과가 낮다. Lazy initialization은 첫 요청 시점에 초기화가 자연스럽게 이루어지므로 인프라 추가 없이 동일한 결과를 낸다.
**트레이드오프**: 자정 이후 첫 요청 전까지 전날 토큰 상태가 유지된다. 사용자가 자정 직후 바로 접속하지 않으면 체감하기 어려운 차이다.

---

### ADR-008: LLM·ecologits 호출을 FastAPI에서만 처리
**결정**: OpenAI API, ecologits 호출과 모든 토큰 회계 로직은 FastAPI 백엔드에서만 수행한다. Next.js 클라이언트는 API 키를 보유하지 않는다.
**이유**: API 키가 클라이언트에 노출되면 키 유출과 비용 어뷰징 위험이 있다. 토큰 차감 로직을 서버에서만 처리해야 클라이언트 조작으로 토큰을 속이는 것을 막을 수 있다.
**트레이드오프**: 모든 AI 요청이 FastAPI를 경유하므로 레이턴시가 소폭 증가한다.
